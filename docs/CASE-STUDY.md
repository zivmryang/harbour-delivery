# Harbour Delivery：AI 辅助 ICT 项目交付工作台

**首版开发日期：2026-10-29。项目类型：AI 辅助设计与开发的 ICT 交付原型。**

本文记录产品需求、系统架构、模型实验与验证过程。内置组织、人员、预算、项目日期及流程改善数字均为模拟数据；模型训练与评估记录来自实际运行。演示场景中的日期独立于产品开发日期，业务收益尚待真实使用环境验证。

## 1. 问题定义与完成范围

ICT 交付涉及客户、供应商、工程人员和运营支持。任务完成、依赖解除、验收通过和服务移交是不同状态；仅有一个看板或一段流畅的 AI 总结，容易掩盖这些区别。

本项目从售前资料移交开始：**把招投标文件、合同、任务书中的要求，与所选政策、法规及技术参考连接，生成带原文引用的项目初稿；经人工审核后，将任务、风险、验收和后续报告放入同一份可导出的工作区。**

模型负责逐段分类、提取、跨文档分析和方案建议；程序保留原文、检查引用及部分明确数值约束；审核人解决冲突并确认计划。未知信息不会自动成为合同事实。

目标使用场景包括网络与视频系统实施、内部流程改善、迁移与服务交接。当前实现支持单浏览器本地工作区，不包含多租户协作、SSO、在线供应商同步或企业级审计。

验收范围包括：

0. 浏览器读取文本 PDF、DOCX、TXT/MD/CSV；本地 Qwen3 8B 分阶段提取及综合，生成任务、里程碑、风险、引用与待确认事项。官方知识来源保留版本及刷新状态，行业或技术参考可自行上传。审核后新增项目并保存原始资料和审核选择。

1. 项目和任务可创建及编辑，RAID 可记录并更新状态；工作区可保存及整体导出。
2. 看板、列表与排期使用同一数据；依赖循环、未完成前置条件及缺失验收证据受到控制。
3. 规则简报与模型简报清楚区分；报告有来源，模型报告为待复核草稿；源数据更新后旧报告提示过期。
4. 标准／Jira 风格／部分中文列 CSV 可交换，JSON 可完整备份；未知状态与坏数据被拒绝。
5. 本地模型能够实际推理，并有一次独立、可复现的微调实验。
6. 模拟业务效果、个人测量和实际模型评估分别标识，成果具有明确边界。

## 2. 实现过程与审核边界

项目使用 AI 编码代理辅助方案细化、代码编写、合成数据构造、训练执行、测试及文档整理。实际执行结果保留在训练日志、预测文件和测试记录中。

产品将不同类型的判断分开处理：

- 确定性代码负责日期、金额、依赖、验收字段和输入结构校验。
- 模型负责结构化抽取和报告草稿，不直接修改任务或批准验收。
- 使用者负责核对原始记录、处理未覆盖的语义错误，并决定是否采纳建议。
- 自动化测试和产物哈希验证支持复现，但不能替代真实使用环境的验收。

## 3. 技术方案与取舍

```text
浏览器工作区（React / TypeScript）
  ├─ 项目、任务、RAID、验收与测量
  ├─ 确定性规则、日历天 FS 关键路径、报告指纹
  ├─ localStorage + JSON 备份 + CSV 交换
  └─ Node AI 网关
       ├─ Ollama / Qwen3 0.6B：项目简报草稿
       ├─ MLX / Qwen3 0.6B + QLoRA：五字段抽取
       └─ OpenAI Responses：可配置的服务端适配器
```

| 决策 | 原因及代价 |
|---|---|
| 借鉴多个工具的管理模式 | Jira/Linear 的明确状态、Project/P6 的依赖思维、Notion 的知识上下文和 Smartsheet 的控制台账，共同服务一个交付问题。没有声称连接这些厂商账户；跨工具能力目前为 CSV/JSON。 |
| 确定性规则先处理验收与计算 | 是否逾期、依赖是否完成、金额和日期是否合法，应可重复验证。模型不能代替验收批准。 |
| 规则、简报模型、抽取模型分开 | 每种能力有不同验收方式。抽取 adapter 的测试结果不扩展为项目规划或长报告能力声明。 |
| 单浏览器存储与静态前端 | 便于演示、备份和保留数据控制；不提供多人实时协作。GitHub Pages 可承载界面和实验记录，实时模型需要另行运行本地服务。 |
| 小模型本地运行 | 在 16 GB Apple Silicon 上实际验证部署与微调过程；能力有限，因此输出校验和失败记录是产品的一部分。 |
| 日历天、完成到开始依赖 | 实现可解释的关键路径与松弛量分析；不含工作日历、资源平衡、原生 `.mpp`/`.xer` 文件或大型 EPC 排程能力。 |

详细工具对应关系见 [TOOL-CHOICES.md](TOOL-CHOICES.md)。API 凭据只保留在服务端，网关具有请求大小、来源、超时、访问令牌及输出验证控制；当前原型不是生产级安全认证。

## 4. 实际验证与指标

2026-10-29 的最终本地验收中，`npm run check` 实际通过 **69 项测试，3 个测试文件**：领域控制 20 项、CSV 10 项、网关 39 项，并完成 TypeScript 与生产构建检查。覆盖关键路径分支／循环、完成关卡、源数据变化、数据结构及日期验证、CSV 公式注入、中英文列映射、来源引用、鉴权、明确完成状态冲突及异常响应等。浏览器实测与未完成的验证见 [VERIFICATION.md](VERIFICATION.md)。

真实本地推理证据包括：

- [Ollama 简报调用](../server/live-smoke.json)：调用真实模型并校验来源编号；记录了仍需修改的文字与遗漏，不能把“请求成功”当作内容质量全部通过。
- [MLX 直接 HTTP 测试](../training/results/server-smoke.json)：使用已训练 adapter，新的合成中文记录五字段全对。
- [网关至 MLX 测试](../training/results/gateway-smoke.json)：真实端到端调用五字段全对；单次耗时 473 ms，不构成速度基准。

QLoRA 实验采用 96 条训练、16 条验证、16 条独立测试记录。模板、来源编号、负责人命名空间和主题按组划分；全部数据合成。固定模型版本、seed、贪心解码和 60-step 训练计划，保留所有测试预测。

| 指标 | 基座 | 微调后 |
|---|---:|---:|
| 严格 JSON／schema 合格 | 0/16 | 14/16 |
| 移除单一围栏后的 schema 合格 | 11/16 | 14/16 |
| 字段准确率 | 69/80（86.25%） | 77/80（96.25%） |
| 来源编号正确率 | 16/16 | 16/16 |
| 整条记录五字段全对 | 8/16 | 13/16 |

基座经常使用 Markdown 围栏，所以格式与语义分开评分。16 条测试只能支撑这一小规模实验；不能据此宣称真实客户准确率、项目交付提速或节省人力成本。

## 5. 遇到的失败与处理

| 观察到的问题 | 本次处理 | 仍然存在的边界 |
|---|---|---|
| 基座输出带代码围栏，严格 JSON 分数为零 | 同时发布严格格式指标和只移除单一围栏的字段指标，保留原始输出 | 避免用格式变化夸大语义提升；两个模型使用相同评价规则。 |
| 微调后 3 条记录把缺失值写成字符串 `unknown` | 保留失败样例，网关检查字段类型、日期及原文依据 | 没有通过偷偷修改测试标签或再次训练消除错误；仍需人工处理缺失信息。 |
| 一个额外英文例子把 `Mei` 改写成 `MEI` | 初次网关拒绝；之后增加只恢复原文中唯一匹配大小写的确定性处理，并返回 normalization 记录 | 对歧义或无原文依据的值继续拒绝；该处理未计入已公布的原始模型评估分数。 |
| MLX 请求原始模型名可能绕过 adapter | 本地服务固定模型版本与 adapter，网关请求 `default_model`，实际调用验证 | 配置变更需重新测试，不能只靠 `/health` 就断言使用了正确模型。 |
| 简报来源编号存在，但文字仍可能不准确或遗漏 | 来源检查之后保留人工复核；记录真实失败与待改进项 | 来源 ID 合法不是内容真实的充分条件。 |
| 实际简报两次把尚未完成的任务描述为已完成 | 保留原始观察，增加摘要、决策和行动中明确完成声明与任务验收状态的冲突检查；重现样例作为回归测试 | 有限规则不能保证任意转述正确；规则简报仍为默认，0.6B 自由文本简报需要人工核对。 |

验证 loss 在第 30 步为 0.106，第 60 步回升至 0.152；本次按固定计划保留最终 adapter，没有依据测试集挑选最好模型。这是后续扩大验证与改善训练设计的依据。

## 6. 如何复现与核对

应用与网关：

```sh
npm ci
npm run check
npm run server
# 另一个终端
npm run dev
```

本地简报需要 Ollama 的 `qwen3:0.6b`；微调抽取服务的环境、模型下载、训练和启动步骤见 [LOCAL-MODEL.md](LOCAL-MODEL.md)。已经训练好的约 2.9 MB adapter（2,895,443 bytes）与模型版本记录保留在仓库中；基座另行下载。运行已包含的 adapter 无需再次训练；完整实验重跑应在单独副本中进行，以保留已发布的原始证据。

仅核对公开实验是否与当前文件一致，无需模型或 GPU：

```sh
python3 training/verify_artifacts.py
```

该命令检查 adapter／配置／数据／预测 SHA-256、分组一致性，按保存的原始输出重新计算分数，并验证公开失败清单及已保存的 HTTP 冒烟结果。它校验仓库内证据一致性，不是第三方认证。重新运行真实推理时使用 `training/smoke_server.py`。

2026-10-29 已发布到[公开 GitHub 仓库](https://github.com/zivmryang/harbour-delivery)和[在线演示站](https://zivmryang.github.io/harbour-delivery/)。[Actions 验证与部署](https://github.com/zivmryang/harbour-delivery/actions/workflows/pages.yml)记录各版本运行结果，公开页面已实测。GitHub Pages 展示应用与实验记录；模型训练和实时推理在本机运行。

## 8. 技术常见问题

**为什么要做微调，提示词不够吗？** 这次实验是比较固定提示下的基座和小型适配器，用来学习数据、评估与部署流程。结果显示特定任务改善，也暴露缺失值错误。它没有证明微调在成本和质量上优于所有提示词或规则方案；真实采用前应增加规则、提示优化等基线。

**为什么不是把 Jira、Planner 等全部接起来？** 本次先验证统一事实、依赖和验收流程，采用明确的 CSV/JSON 交换。完整连接器需要真实租户授权、字段映射、冲突处理和端到端测试，不应因为有工具名称就宣称已经集成。

**模型给错答案怎么办？** 展示已保留的失败，说明可验证字段的确定性检查、来源约束、拒绝机制和人工复核；无法用规则验证的建议保持草稿状态，不自动修改项目或批准验收。

**如何证明业务价值？** 当前只有实际技术评估和模拟业务台账。真实试点应在使用前约定基线、同类样本、包含复核的总耗时、质量、采用情况和验收人，然后报告实际结果。

**下一步优先做什么？** 先取得一个真实组织的有限范围试点，确定使用者与验收条件；在其实际数据与工作约束下验证是否值得采用。需要扩展模型时，新增独立测试场景，避免围绕这 16 条记录优化。


## 资料移交建项的边界

[文档建项引擎](HANDOVER-ENGINE.md)和[知识来源目录](KNOWLEDGE-SOURCES.md)记录了处理步骤、运行限额与失败行为。Qwen3 8B 的资料分析、0.6B 的报告生成和 MLX 微调五字段抽取是三个独立任务；不能把五字段测试准确率用作合同分析准确率。

当前知识库包含六条经过核查的香港官方来源入口，并支持上传自备资料；没有声称覆盖所有行业、地区或最新法条。扫描 PDF 需要先做 OCR，图表含义仍需核对。项目配置是待审草稿，不自动审批合同、不替代法律判断，也不执行实际采购或对外发送指令。
